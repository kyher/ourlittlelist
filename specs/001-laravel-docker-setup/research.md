# Research: Application Foundation & Containerised Environment

Versions were checked against Packagist and the starter kit's GitHub `main` branch on 2026-11-06.

## R1. Framework & starter kit version

- **Decision**: Laravel 13 (framework ^13.17, currently 13.40) with the official Livewire starter
  kit from its `main` branch. This brings Livewire 4, Flux UI 2, Laravel Fortify (auth backend),
  Tailwind CSS and Vite.
- **Rationale**: The constitution mandates the Livewire starter kit. The Laravel installer builds
  new apps from the kit's `main` branch, which tracks Laravel 13 and Livewire 4. The tagged
  Packagist release (v1.0.1, Feb 2025) is outdated (Laravel 12, Volt) and must not be used.
- **Alternatives considered**: `composer create-project laravel/livewire-starter-kit` (resolves
  to the stale v1.0.1 tag, rejected). Plain `laravel/laravel` with auth added by hand (violates
  Principle I).

## R2. Bootstrapping without host PHP

- **Decision**: Scaffold once using the Laravel installer inside a throwaway Composer/PHP 8.4
  container: `laravel new` with the `--livewire --pest` options. Scaffold into a temporary
  directory, then move the files into the repo root, because the root already holds `.specify/`,
  `.claude/` and `specs/`. On a fresh clone, run the documented one-off
  `docker run … composer install` (Sail's documented pattern) to create `vendor/` so Sail
  can start.
- **Rationale**: Meets FR-001 and Principle II (no PHP/Composer on the host is required, even
  though this machine happens to have them). It also follows Sail's own documented approach.
- **Alternatives considered**: Using host PHP/Composer (breaks the "Docker only" promise).
  A custom Dockerfile build stage that runs composer (more moving parts than Sail).

**Actual command used (2026-11-06, Laravel Installer 5.32.0)**:
`docker run --rm -u "$(id -u):$(id -g)" -e COMPOSER_HOME=/tmp/composer -e HOME=/tmp -v "<scratch>:/app" -w /app laravelsail/php84-composer:latest bash -c "composer global require laravel/installer -q && /tmp/composer/vendor/bin/laravel new ourlittlelist --livewire --pest --database=mysql --no-node --no-boost --no-interaction"`,
then `php artisan sail:install --with=mysql,mailpit --php=8.4` in the same image. `--no-node` was
needed because the Composer image has no Node; npm runs later through Sail.

## R3. Container orchestration

- **Decision**: Laravel Sail (`compose.yaml` generated by `sail:install`). The `laravel.test`
  service uses the PHP 8.4 runtime and includes Node for Vite. Services: `mysql`
  (MySQL 8.4 LTS) and `mailpit`.
- **Rationale**: Sail is first-party (Principle VI). It bundles PHP, Node and Composer and wires
  `.env` defaults. MySQL is Sail's most widely used database and its data volume persists across
  restarts (FR-006). Mailpit gives a browser mail viewer (FR-007). Sail's MySQL service has a
  healthcheck, and the app waits for it with `depends_on`, which covers the "database not ready"
  edge case.
- **Alternatives considered**: PostgreSQL (equally viable, but Sail's MySQL is the default path,
  so no advantage). A hand-written compose file with nginx and php-fpm (more config to maintain,
  and only production-like, which is out of scope). Redis for cache, queue and session (YAGNI:
  the database drivers are the starter kit's defaults and are enough for two users per couple).

## R4. Testing framework

- **Decision**: Pest (the installer's `--pest` option converts the kit's PHPUnit tests). Tests
  run with `sail artisan test` (or `sail pest`), using in-memory SQLite per `phpunit.xml`.
- **Rationale**: The constitution names Pest as preferred and allows SQLite for tests. In-memory
  SQLite keeps the suite fast (SC-004), and tests stay isolated from development data.
- **Alternatives considered**: The kit's default PHPUnit (allowed, but not the preferred option).
  Testing against the MySQL container (slower, adds no value for this feature).

## R5. Auth feature set

- **Decision**: Keep the kit's Fortify features as shipped: registration, login, logout, password
  reset, password confirmation, profile update, account deletion, appearance settings, and
  optional two-factor authentication (the user opts in). Email verification stays optional, matching the spec's assumptions. The kit now enables
  `MustVerifyEmail` on `User` by default, so it was removed during implementation. The kit also
  ships passkey sign-in (Fortify `passkeys` feature), which is kept as an opt-in.
- **Rationale**: Principle I says to build on the kit's flows rather than re-implement them, and
  removing working, tested features costs effort for no gain. Two-factor is off unless a user
  enables it.
- **Alternatives considered**: Removing 2FA (unnecessary churn). Enforcing email verification
  (deferred to the couple-connection feature).

## R6. Environment & port configuration

- **Decision**: In `.env.example`, set `APP_NAME="Our Little List"`, `DB_CONNECTION=mysql`,
  `DB_HOST=mysql`, `MAIL_MAILER=smtp` and `MAIL_HOST=mailpit`, keep the `database`
  session/cache/queue drivers, and expose `APP_PORT`, `VITE_PORT`, `FORWARD_DB_PORT` and
  `FORWARD_MAILPIT_DASHBOARD_PORT` (Sail's variables). `.env` stays ignored by git.
- **Rationale**: Meets FR-008, FR-009 and FR-011, and covers the port-conflict edge case without
  editing committed files.

## R7. Code style & static analysis

- **Decision**: Laravel Pint (`sail bin pint --test` as the check, `composer lint` to fix).
  Larastan ships with the kit and is kept, but it is not a merge gate in this feature.
- **Rationale**: The constitution makes Pint a quality gate. Larastan is free to keep. Making it
  a gate can be revisited later.
